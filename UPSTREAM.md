# Upstream integration contract

Blue Pine Solutions Mail is a downstream distribution of Mailflare. This file records where Blue Pine follows upstream, where it diverges, and how upstream changes are brought in. Read it before any architectural change.

|---|---|
| Blue Pine public source and releases | https://github.com/blue-pine-solutions/blue-pine-mail (`public`) |
| Blue Pine development | Blue Pine's private development repository (`origin`) |
| Upstream | https://github.com/hieunc229/mailflare (`upstream`) |

Update these SHAs after every upstream integration. The next integration merges new upstream commits on top of the current upstream base.

## Boundary

### Preserve / follow upstream

Changes here come from upstream. Blue Pine fixes in these areas must stay upstream-compatible and should be offered upstream.

- Upstream database schema (`src/db/schema/index.ts`): every upstream table and column.
- Upstream migrations (`drizzle/migrations/`): verbatim and in upstream order.
- Backup format and required table set (`src/lib/backups/`).
- Persisted storage markers and layouts (stored HTML markers, bucket key prefixes, `/data`).
- Mail engine: intake, inbound pipeline, outbound pipeline, threading, spam, search, folders, contacts, calendar, attachments.
- Routing semantics (`src/lib/email/routing.ts` phase order and rule scopes).
- SMTP behavior (`server/runtime/smtp.ts`).
- JMAP behavior (`src/lib/jmap/`).
- API v1 routes and API-key scopes (`/api/v1/*`).
- MCP tool names and schemas.
- The relay protocol (`deploy/cloudflare-email-relay` ↔ `/api/inbound`).
- `X-Mailflare-*` technical protocol headers.
- Calendar UID compatibility.
- Authentication and security engine (sessions, MFA, password reset, registration rules).
- Runtime contracts (`getEnv()` / `CloudflareEnv` shape, Workers and Node runtimes).
- Existing environment-variable names.
- Internal technical identifiers wherever renaming would break compatibility.

### Blue Pine owns

Changes here are Blue Pine decisions. Upstream changes in these areas are translated or ignored.

- Distribution identity (product name, icon defaults, version display).
- Feature policy (which capabilities a deployment enables).
- Commercial policy.
- Customer branding policy.
- Legal and source surfaces (`NOTICE`, source links, attribution).
- Update and release channel.
- Managed deployment and operations.
- Blue Pine documentation.
- Guard tests and downstream engineering rules (`tests/distribution-guard.test.mjs`, this file, the Blue Pine section of `CLAUDE.md`).

Optional features (custom branding, multiple accounts, shared mailboxes, account forwarding) are gated by the Blue Pine feature policy in `src/lib/distribution/features.ts`. Upstream's Paymug licensing layer (`src/lib/licenses/`, `/api/licenses`, the Licenses page and Upgrade pill) is removed. The `license_settings` table is kept, unused, for schema and backup compatibility.

## Customer releases

Upstream Mailflare is an engineering input, never a customer update channel. Installations only learn about approved Blue Pine Solutions Mail releases: published (non-draft, non-prerelease) GitHub Releases tagged `bluepine-vMAJOR.MINOR.PATCH` in the Blue Pine repository, compared against `DISTRIBUTION.version`. The app checks for them but never installs or deploys; a release is rolled out with the installation's deployment method. Publish a release only for a commit that has passed the integration checks below.

The public repository is the Corresponding Source for every build offered to users. Publish a commit there, by pushing it with an explicit refspec (`git push public <sha>:refs/heads/main`, never `--all`, `--mirror` or `--tags`), before any installation runs it, and confirm with `npm run release:verify-source -- <sha>` that `/source` for that build resolves publicly.

## Integration process

1. Work on a dedicated branch: `integrate/upstream-<YYYY-MM-DD>` from Blue Pine `main`.
2. Pin a specific upstream SHA (upstream does not tag releases). Record it in the table above.
3. For routine integrations, **merge** the pinned SHA; do not re-create upstream history with wholesale cherry-picks. Merging preserves ancestry, so the next integration only sees new upstream commits.
4. Resolve by boundary:
   - **Engine changes** are reviewed and normally accepted. Re-apply Blue Pine engine fixes if upstream has not taken them.
   - **Product-layer changes** are translated or ignored; Blue Pine's version wins.
   - **New upstream license or product gates** must not simply be accepted. Translate them to Blue Pine feature policy; changes to upstream's removed licensing files are dropped.
   - **Upstream migrations** are accepted verbatim and in order. Never edit a historical upstream migration, never skip or reorder one.
5. Before merging the integration branch into `main`, run the full checks: `npm run lint`, `npx tsc --noEmit`, `node --test tests/*.test.mjs`, `npm run build:node`, a Docker smoke test, and an upgrade test against a copy of an existing data volume.
6. Merge into `main` through a reviewed pull request with a merge commit.
7. **Security fast lane:** an urgent upstream security fix may be cherry-picked directly onto `main` and released. The next scheduled merge reconciles it.

## Downstream migrations

Blue Pine may own schema for Blue Pine features (for example mail app passwords). Upstream migrations stay verbatim and in upstream order; Blue Pine migrations live beside them in a separate namespace that every migration runner orders after them.

### How the runners behave

There are three runners, and all of them record applied migrations by file name in `d1_migrations`, so a file applies once per database whatever its position:

| Runner | Used by | Order |
|---|---|---|
| `server/runtime/migrate.ts` | Node / Docker, at start | `drizzle/migrations/meta/_journal.json` entries first, then every other `.sql` file by JavaScript string order |
| `src/lib/migrations/service.ts` over `bundle.json` | Workers: setup and Admin → Version and updates | every `.sql` file by JavaScript string order (`scripts/generate-migration-bundle.mjs`) |
| `wrangler d1 migrations apply` | `npm run migrate`, `db:migrate:*` | files with a numeric prefix by that number, then files without one by string order |

Upstream's hand-written `0021_add_api_keys_prefix_index.sql` is not in the journal, so the Node runner applies it after `0040` while the other two apply it after `0021_add_mailbox_signature.sql`. That existing difference is harmless because the statement is independent, and it shows the rule Blue Pine migrations must follow: never depend on a position relative to an upstream migration that is not already applied.

### Naming and ordering

- Blue Pine migrations are named `bpNNNN_<snake_case_description>.sql`: lowercase `bp`, four digits starting at `0001`, contiguous, never reused. Example: `bp0001_add_mail_app_passwords.sql`.
- `bp` sorts after every digit and has no numeric prefix, so all three runners apply Blue Pine migrations after every upstream migration present in the same build, in `bpNNNN` order. Wrangler's next-number logic ignores them, so upstream-style numbering is unaffected.
- Blue Pine migrations are hand-written and never listed in the drizzle journal. Blue Pine tables are declared in `src/db/schema/bluepine.ts`, which drizzle-kit does not read (`drizzle.config.ts` points at `index.ts`), so a future `drizzle-kit generate` never emits an upstream-numbered copy of them.
- A Blue Pine migration may depend only on upstream schema that existed when it was written. On a database created later, upstream migrations newer than it run before it; on an existing database they run after it. Write Blue Pine migrations so either order gives the same result, and never alter, drop or rebuild an upstream table from one.

### Ownership and changes

- Blue Pine owns `bp*` files and `src/db/schema/bluepine.ts`. Upstream owns every numbered file.
- Never edit a `bp` migration once it has been merged to `main`: installations have recorded it. Fix forward with the next `bpNNNN`.
- Never rename, renumber or delete one. There is no down-migration; recovery is a restore from backup (below) or a forward fix.
- `tests/downstream-migrations.test.mjs` enforces the naming, contiguity, journal exclusion, ordering in all three runners and the rebuild guard below.

### Upstream merges

- Upstream never touches `bp*` files, so file-level conflicts cannot occur. A conflict in `src/db/schema/index.ts` or `src/lib/backups/` is resolved in upstream's favour, then Blue Pine's additions (below) are re-applied.
- **Table rebuilds.** SQLite changes some columns by creating a new table, copying, dropping the old one and renaming. Dropping a table drops its triggers, and on D1 (where foreign keys cannot be switched off) the drop can cascade into child tables. Blue Pine migrations attach triggers or foreign keys to `users`, `mailboxes`, `domains` and `mailbox_access`, exactly two triggers to `messages` (bp0003 and bp0004) and two to `message_attachments` (bp0004); see "IMAP \Deleted invariant (bp0003)" and "IMAP draft UID invariant (bp0004)". The guard test fails if any upstream migration drops or renames one of those tables. When it fails during an integration: verify on a copy of real data what happens to `mail_app_passwords` and `imap_message_uids` rows, and add a `bpNNNN` migration that recreates the Blue Pine triggers (and repairs data if the cascade removed it) before merging.
- **Triggers and indexes.** Blue Pine triggers are named `bp_*` and Blue Pine indexes carry the Blue Pine table's name, so they cannot collide with upstream names. Check new upstream triggers on the same tables for interaction (upstream's own are `messages_fts_*` and `jmap_messages_*`, on `messages`, beside Blue Pine's `bp_imap_membership_clears_deleted` and `bp_imap_draft_content_releases_uid`; upstream has none on `message_attachments`).

### Backups

- Every Blue Pine table must be listed in `DOWNSTREAM_BACKUP_TABLES` and assigned to a group in `src/lib/backups/table-groups.ts` in the same change that creates it; the coverage check aborts backups otherwise, and it must not be weakened.
- Downstream tables are written under `tables` but never listed in `includedTables`. Upstream Mailflare rejects a document whose `includedTables` names a table it does not know, and ignores extra entries under `tables`, so Blue Pine backups stay restorable into upstream (dropping the Blue Pine data) and upstream backups restore into Blue Pine (leaving the Blue Pine tables empty). The backup format id and version stay `mailflare-database-backup` / `1`.
- A restore replaces Blue Pine tables like every other table: the database returns to the state of the backup, including credentials revoked since. Restoring a backup into a build that has not applied a Blue Pine migration yet fails with an instruction to apply pending migrations first when the backup carries rows for that table.

### Certification for a new Blue Pine migration

Before a `bp` migration reaches `main`: `node --test tests/*.test.mjs` (fresh database, existing-database upgrade, second run applies nothing, ordering, backup coverage and round-trip), `npm run build` (the bundle contains the file last), `npm run build:node` and a Node start against a copy of an existing data volume (only the new file applies, a restart applies nothing), `wrangler d1 migrations apply --local` against an existing local database, and a backup and restore on the upgraded database.

## IMAP mailbox state

`src/lib/imap/` holds the storage contract the IMAP listener consumes (see "IMAP listener" below); it has no parser or protocol dependency of its own. It reads the upstream mail model and writes to it in exactly four ways, the first three through the columns the web app itself changes and the fourth by deleting rows as JMAP's second destroy does, so the upstream revision triggers on `messages` report every change to web and JMAP clients:

- `storeImapFlags` (A5.1) sets `messages.read` and `messages.starred`, like the web app's read and star actions and JMAP keywords. Each write is keyed by the UID mapping *and* current folder membership, so a stale UID changes nothing; clearing \Seen never writes outbound mail, which is always \Seen.
- `expungeImapFolder` (A5.2a) sets `status = 'trash'` and `folder_id = NULL` on messages marked \Deleted, like the web app's Trash action; see "Recoverable expunge (A5.2a)". It never deletes a row or a stored object.
- `moveImapMessages` (A5.2b) sets `status` and `folder_id` to a destination folder's, like the web app's move actions; see "IMAP MOVE (A5.2b)". It never deletes a row or a stored object. After a move into or out of Spam, `trainImapSpamFeedback` trains the upstream spam filter through upstream's own `src/lib/spam/feedback.ts`, as the web app's spam buttons do.
- `expungeImapFolder` in Trash and Drafts (A5.2c) deletes `messages` rows marked \Deleted, letting upstream's foreign keys and triggers cascade, and then their stored objects; see "Permanent IMAP expunge (A5.2c)".

Everything else IMAP keeps (UIDs, \Deleted) is in the Blue Pine tables.

- **Folders.** INBOX (`status = 'received'`, no folder), Drafts (`draft`), Sent (`sent`), Archive (`archived`), Spam (`spam`, special-use Junk), Trash (`trash`) and one folder per row of `folders` (`received` mail filed there). This is the web app's partition: a custom folder only holds `received` mail, so a message moved to Trash from a folder is in Trash. Queued and failed sends are not IMAP-visible (their representation is generated per read), and snoozing does not hide mail, as in JMAP.
- **Identity.** `imap_folders` keeps UIDVALIDITY and UIDNEXT per (mailbox, folder key); `imap_message_uids` keeps the UID a message holds in the folder it is in. A message that leaves a folder (any status or folder change, or deletion, by any code path) loses that UID the next time the folder is read and receives the next UID of its new folder; UIDs are never reused, because UIDNEXT only increases (enforced by triggers) and moves inside the same statement that assigns UIDs. A folder's existing mail gets UIDs on its first read, oldest first (`created_at`, then `id`), in bounded chunks. Draft UIDs are bound to A1's draft fingerprint and to the stored object first served, so an edited draft gets a new UID instead of new bytes under an old one.
- **UIDVALIDITY** is set when a folder's state row is created (the current Unix time, above every value the mailbox has used) and changes only when a restore replaces state clients may have seen (`src/lib/imap/restore.ts`). Upgrades and restarts never change it.
- **Certified triggers on `messages` and `message_attachments`, nothing on `folders`.** Blue Pine state has no foreign key to any of them and is reconciled by join on read, so an upstream rebuild cannot drop it. The exceptions are `bp_imap_membership_clears_deleted` (bp0003) and bp0004's three draft triggers, described below; the rule that nothing attaches to `messages` is superseded for those triggers only. The guard test fails if a Blue Pine migration attaches to an upstream table outside the anchored list, attaches any other trigger or any foreign key to `messages` or `message_attachments`, or if an installed trigger differs from its certified definition.
- **\Deleted** is kept per UID in `imap_message_uids.deleted`: it survives reconnects, every session selecting the folder sees it, and it is gone when the message leaves the folder (the UID is released). Only a principal with management access (`full_access`, the owner, or an admin) may change it, and only while bp0003's trigger exists; in Drafts only while bp0004's triggers exist too, and only on the principal's own drafts (`messages.user_id`, checked against current state and guarded inside the write). A read-only or send-only delegate naming \Deleted is `denied`, as is setting it on another user's draft, and the whole STORE writes nothing.

### IMAP \Deleted invariant (bp0003)

**Invariant.** A message's pending \Deleted marks are cleared whenever the columns that decide its IMAP folder change: `mailbox_id`, `status` or `folder_id` (the inputs of `membershipCondition`). The trigger:

```sql
CREATE TRIGGER `bp_imap_membership_clears_deleted` AFTER UPDATE OF `mailbox_id`, `status`, `folder_id` ON `messages`
WHEN OLD.`mailbox_id` IS NOT NEW.`mailbox_id` OR OLD.`status` IS NOT NEW.`status` OR OLD.`folder_id` IS NOT NEW.`folder_id`
BEGIN
	UPDATE `imap_message_uids` SET `deleted` = 0 WHERE `message_id` = NEW.`id` AND `deleted` = 1;
END;
```

It only ever clears marks; it never sets one, touches UIDs, or writes `messages`. Read, starred, snooze and content changes do not fire it. SQLite fires it for `folder_id` set to NULL by the foreign key when a custom folder is deleted.

**Why it must attach to `messages`.** UIDs are released lazily, when a folder is next read. A message that left a folder and came back before anyone read it would otherwise find its old UID still marked \Deleted, and a later EXPUNGE would act on a mark that no longer expresses anyone's intent. Moves happen in many code paths (web actions, bulk actions, JMAP, the agent tools, spam feedback, inbox rules, folder deletion), and `messages` keeps no per-message change counter, so no application hook can see a message leave and return. A trigger on the columns is the only complete detection.

**Fail closed.** The IMAP service offers \Deleted (in PERMANENTFLAGS), STORE of \Deleted, EXPUNGE and MOVE only while the trigger exists (`hasDeletedInvariant` in `src/lib/imap/state.ts`, read on every operation, never cached), and every write that sets \Deleted or relocates a message also carries the check inside its own SQL, so it does nothing if the trigger disappeared after the check. Without the trigger, STORE naming \Deleted, EXPUNGE and MOVE answer `NO [CANNOT]`, CLOSE expunges nothing, and \Seen and \Flagged keep working. MOVE needs it because a destination UID left from an earlier stay could otherwise still carry a stale \Deleted mark.

**Checked upstream history.** Upstream migrations `0000`–`0046` were checked: none drops, renames or rebuilds `messages`. `messages` is therefore in the anchored-table guard, which fails on any future upstream migration that does.

**Future upstream certification.** When an integration touches `messages`:

1. If the anchored-table guard fails (a rebuild, drop or rename of `messages`), the rebuild drops `bp_imap_membership_clears_deleted`. Add a `bpNNNN` migration that recreates it exactly (and clears `imap_message_uids.deleted` for every row, since marks may have gone stale while it was missing) before merging. Until then the listener fails closed.
2. If the meaning of `status`, `folder_id` or `mailbox_id` changes, or another column starts to decide folder membership, the trigger's column list must follow `membershipCondition`.
3. `tests/downstream-migrations.test.mjs` (exact trigger text, the only Blue Pine objects on `messages`), `tests/imap-expunge.test.mjs`, `tests/imap-move.test.mjs` and `node scripts/imap-state-d1-check.mjs` must pass on the integrated tree.

### Recoverable expunge (A5.2a)

`expungeImapFolder` moves the messages of a folder that are marked \Deleted to Trash (`status = 'trash'`, `folder_id = NULL`), the same state the web app's Trash action produces and JMAP's first `Email/set destroy` produces. Nothing is deleted: the row keeps its read and starred state, date (INTERNALDATE), stored bytes (so RFC822.SIZE) and attachments, and gets a new Trash UID without \Deleted. In Trash and Drafts, EXPUNGE is permanent instead; see "Permanent IMAP expunge (A5.2c)".

Each chunk of at most 80 UIDs is authorized afresh and moved by one D1 batch (`relocateImapMessages` in `src/lib/imap/state.ts`), a transaction on D1 and on the Node wrapper, whose statements each guard themselves: the product move only for messages still in the source folder whose source UID is still marked \Deleted (and only with bp0003 installed); destination UIDs from UIDNEXT, in source UID order, for messages that are now in Trash and hold no Trash UID yet; release of source UIDs whose message left. A repeated or stale request changes nothing, a concurrent web or IMAP move wins, and any failed statement (an exhausted UIDNEXT, for example) rolls the whole chunk back. MOVE (A5.2b) reuses the primitive without the \Deleted guard.

### IMAP MOVE (A5.2b)

`moveImapMessages` moves the messages that a set of UIDs names from one folder to another folder of the same mailbox. It needs what EXPUNGE needs: management access (`denied` otherwise) and bp0003 (`unsupported` otherwise). Destinations follow `imapMoveTarget` (`src/lib/imap/utils.ts`), which mirrors the web app's moves:

| Source | Allowed destinations | Refused |
| --- | --- | --- |
| INBOX, custom folder, Archive | INBOX, custom folder, Archive, Spam, Trash | Sent, Drafts, itself |
| Spam | INBOX (ham), custom folder, Archive, Trash | Sent, Drafts, itself |
| Trash | INBOX, custom folder, Archive, Spam | Sent, Drafts, itself |
| Sent | INBOX, custom folder, Archive, Trash | Spam, Drafts, itself |
| Drafts | Trash, the author's own drafts only | everything else |

INBOX is `received` without a folder, a custom folder `received` with that folder, Archive `archived`, Spam `spam` and Trash `trash`. Sent and Drafts are never destinations: sending and composing are not moves, and nothing records where a message in Trash came from, so an IMAP client cannot restore a deleted sent message into Sent (the web app can). Sent mail in any folder cannot move to Spam (the web app's report-spam ignores it too). A draft may only be discarded to Trash by its author (`messages.user_id`), like the web app's Drafts delete; the web app's bulk Trash action and JMAP only check management access, so IMAP is the stricter of the two. A move to the folder a message is already in is refused and allocates nothing.

Each chunk of at most 80 UIDs is re-authorized, re-checked (destination still exists, policy, sent mail into Spam, draft authorship) and moved by one `relocateImapMessages` batch that carries the same guards in its own SQL (inbound only into Spam, author only out of Drafts, a custom destination that still exists, bp0003): the message's status and folder, a fresh destination UID from UIDNEXT in source UID order with `deleted` = 0 (bp0003 clears every mark of the message in the same statement), and the release of the source UID. Nothing else changes: row, bytes (the destination UID carries the source UID's recorded canonical key and size), date, read and starred state and attachments stay. A stale sequence number or UID, a message moved or changed meanwhile by any other path, a repeated MOVE and an exhausted UIDNEXT all change nothing (the last rolls the whole chunk back). A later chunk may be refused, or find access gone, after earlier chunks committed; those stay moved and are reported.

**Spam training.** A MOVE into Spam trains the mailbox's filter as spam and a MOVE from Spam to INBOX as ham, for inbound mail only, like the web app's "report spam" and "not spam" (moves from Spam to a custom folder, Archive or Trash train nothing, as in the web app). The training runs after the move committed, never inside its batch, through `recordSpamTraining`, which uses `spamTrainingStatements`: upstream's training extracted from `applySpamFeedback` without the status change, with every statement guarded by the `spam_feedback` row still being what was read, so a retry, a repeated move or a concurrent training counts once. `applySpamFeedback` builds on the same statements and behaves as before. A failure or a crash after the move leaves the message moved and at worst untrained; the listener logs it and still answers OK.

When an upstream integration touches the mail model, certify before merging:

1. `messages.id` values survive any rebuild of `messages` (UIDs refer to them). If ids were rewritten, affected messages simply get new UIDs; raise UIDVALIDITY with a `bpNNNN` migration if the whole mapping should be discarded instead.
2. The meaning of `messages.status` values and of `folder_id` still matches `folderKeyForMessage` and `membershipCondition` in `src/lib/imap/`; a new status must be mapped or deliberately left invisible.
3. `folders.id` stays stable across renames (IMAP keeps UIDVALIDITY through a rename).
4. A rebuild of `mailboxes` is caught by the anchored-table guard (it would cascade into `imap_folders` on D1).
5. `bp_imap_membership_clears_deleted` still exists with its certified definition and its column list still matches `membershipCondition` (see "IMAP \Deleted invariant (bp0003)"); bp0004's triggers still exist with theirs and the content trigger's columns still match `draftFingerprint` (see "IMAP draft UID invariant (bp0004)").
6. `node --test tests/*.test.mjs` (including `tests/imap-state.test.mjs`, SQLite, the A4 listener suites `tests/imap-protocol.test.mjs`, `tests/imap-session.test.mjs` and `tests/imap-listener.test.mjs`, and `tests/imap-flags.test.mjs`, `tests/imap-expunge.test.mjs`, `tests/imap-move.test.mjs`, `tests/imap-permanent-expunge.test.mjs`, `tests/imap-uidplus.test.mjs`, `tests/imap-idle.test.mjs` and `tests/imap-mailbox-management.test.mjs`) and `node scripts/imap-state-d1-check.mjs` (the state layer in workerd over D1 and R2) pass on the integrated tree.

### IMAP draft UID invariant (bp0004)

**Invariant.** A Drafts UID names one version of a draft's content (A3 binds it to A1's `draftFingerprint`). Whenever that content changes, the database releases (deletes) the draft's Drafts UID in the same statement as the change:

- `bp_imap_draft_content_releases_uid`, `AFTER UPDATE OF` exactly the `messages` columns `draftFingerprint` digests (`from_addr`, `to_addr`, `cc_addr`, `bcc_addr`, `subject`, `text_body`, `html_body`, `in_reply_to`, `references_header`), when at least one value actually changes: deletes the message's `imap_message_uids` rows in the Drafts folder of its old or new mailbox;
- `bp_imap_draft_attachment_added_releases_uid` (`AFTER INSERT ON message_attachments`) and `bp_imap_draft_attachment_removed_releases_uid` (`AFTER DELETE`), when the message is a draft: the same, for the attachment's message. Attachment rows are never updated in place (the guard test checks the code), so insert and delete cover every change the fingerprint sees.

They only ever delete Drafts-folder UID rows; they never write `messages` or `message_attachments`, and received mail's UIDs are untouched. The edited draft gets the next UID on the next read, as before; the old UID, and any \Deleted mark on it, is gone.

**Why a trigger.** A draft edit is several separate writes (the columns, then clearing `raw_r2_key`; attachment rows one at a time), the fingerprint is computed in application code, and `messages` has no version column, so no single guarded statement could prove that a UID still names the current content. Without this, an IMAP client could mark draft A deleted, the web app could edit A, and the client's EXPUNGE would destroy the edited draft; or a STORE through an old UID that nobody had released yet could mark it.

**Fail closed.** \Deleted in Drafts, and permanent EXPUNGE and CLOSE there, are offered only while all three triggers exist (`hasDraftInvariant` / `draftInvariantInstalled` in `src/lib/imap/state.ts`, read on every operation and repeated inside every such write). Drafts edited before bp0004 was installed may hold a stale UID; STORE of \Deleted and EXPUNGE in Drafts release stale UIDs first (`releaseStaleDraftUids`, the existing fingerprint binding), and any later edit releases its own.

**Future upstream certification.** If `draftFingerprint` changes the columns it digests, or `messages`/`message_attachments` is rebuilt, add a `bpNNNN` migration that recreates the triggers with the new column list before merging (a rebuild drops them, and Drafts deletion then fails closed until it does). SQLite does not validate an `UPDATE OF` column list, so `tests/downstream-migrations.test.mjs` checks that every listed column exists and matches `draftFingerprint`.

### Permanent IMAP expunge (A5.2c)

In Trash, and in Drafts for the principal's own drafts, EXPUNGE and CLOSE delete messages permanently. The rule is **database truth disappears before any stored byte does**: a crash may leave an orphaned object, never a live row whose bytes were deleted.

1. `expungeImapFolder` refuses first (`denied` without management access, `unsupported` without bp0003, in Drafts without bp0004), then in Drafts releases stale UIDs, and takes the folder's \Deleted UIDs up to the highest UID the session announced (in Drafts, the principal's own drafts only; another user's marked draft is left alone).
2. Each chunk of at most 25 UIDs is re-authorized and deleted by one `deleteImapMessagesPermanently` batch (`src/lib/imap/state.ts`; a transaction on D1 and on the Node wrapper). Its guard, repeated in its own SQL: the message is in the mailbox with status `trash` or `draft`; the exact UID naming it in this folder is in the chunk, at most the announced maximum, and marked \Deleted; the folder row is this mailbox's Trash or Drafts; in Drafts `messages.user_id` is the principal and bp0004 is installed; bp0003 is installed; and the principal's authority still holds (user exists and is enabled, the app password still exists for this user and mailbox, the mailbox exists and is enabled, and the user owns it or has `full_access` while sharing is enabled). The statements: S1 captures the attachment keys of the guarded messages (a `RETURNING` clause sees the table after the cascade, so they must be read first, in the same transaction); S2 `DELETE FROM messages … RETURNING id, raw_r2_key`, exactly what this operation deleted; S3 deletes the deleted messages' UID rows in other folders (`imap_message_uids` has no foreign key to `messages`); S4 releases the chunk's UIDs whose message left the folder. Only S1 keys of messages in S2's result are kept. Upstream's foreign keys do the rest: attachments, shared attachment links, spam feedback, agent draft metadata, send approvals and agent jobs for the message cascade; outbound jobs, audit logs and other agent references are set null; the full-text index and JMAP revisions follow their triggers. Every statement stays below D1's 100 bound parameters (asserted; 40 at a full chunk on D1). Deletion never assigns a UID or touches UIDNEXT.
3. Only after that batch committed, `cleanupDeletedMessageObjects` (`src/lib/imap/cleanup.ts`) removes the raw object and attachment objects, best effort: only keys in the shape a message owns (`inbound/<name>.eml`, `imports/<id>.eml`, `drafts/<id>.eml`, `canonical/<id>/…`, `attachments/<id>/<attachment>/<file>`; never `backups/`, uploads or another message's key) and only if no `messages` or `message_attachments` row still references them. A missing object is success; a failure is logged (`expunge.cleanup-failed`, with message id and key, never content) and leaves an orphan. Cleanup never restores a row and never fails the EXPUNGE.

A chunk refused or failing after earlier chunks committed leaves those committed (and cleaned) and reported. CLOSE does the same without untagged responses; if the deletion fails it answers `NO [UNAVAILABLE]` and the mailbox stays selected. The web app and JMAP delete through upstream's `deleteMessageWithObjects`, which is not used here (see below).

**Known limitations and residual risks.**

- **Orphans.** A storage failure or a crash between the commit and the cleanup leaves the objects in storage. Nothing reclaims them yet. A future sweep must only consider message-owned key shapes, re-check references immediately before each delete, keep a minimum age beyond the inbound queue's retry horizon and the backup interval, never delete objects a retained backup's rows reference, and never touch `backups/` or `jmap-uploads/`. The Node file bucket cannot list objects yet.
- **Inbound redelivery.** A received message's row id is derived from its raw key. If the inbound queue redelivers an already-processed message and re-creates its row after the cleanup's reference check but before the object delete, the recreated row can lose its raw bytes. This needs a queue retry to coincide with a permanent deletion of that message within milliseconds, and only affects a message its owner just deleted; the reference check is kept regardless.
- **Backups.** Backups contain the database, not stored objects. Restoring a backup taken before a permanent deletion restores rows whose raw bytes and attachments were since deleted (IMAP FETCH answers unavailable; the web app shows a copy generated from the stored columns). A5.2c does not change this.
- **Web and JMAP deletion.** Upstream's `deleteMessageWithObjects` (JMAP `Email/set destroy` in Trash and Drafts, the web draft delete, agent discard, submission cleanup) deletes objects before the row, by id only, without re-checking state; JMAP destroy also only requires a non-read-only permission and no draft authorship. A5.2c does not change those paths; they remain for a separate remediation (to be offered upstream).
- A send-as or send-on-behalf delegate cannot delete their own drafts over IMAP (management access is required everywhere); the web app lets draft authors delete their drafts.

## IMAP listener

Blue Pine-owned and Node/Docker only: upstream has no IMAP server, and Workers cannot accept TCP. It is IMAP4rev1 over implicit TLS, on top of the A3 contract above; it defines no storage semantics of its own and needs no schema. Its only writes are \Seen and \Flagged (A5.1), \Deleted with recoverable EXPUNGE and CLOSE (A5.2a), MOVE with its spam training (A5.2b), permanent EXPUNGE and CLOSE in Trash and Drafts (A5.2c), UID EXPUNGE through those same paths (A5.3), folder management through R-1 (A5.5a), and drafts created by APPEND (A5.7).

- **`src/lib/imap-server/`** is the protocol engine: framing, grammar, session state, mailbox names, FETCH, MIME structure, ENVELOPE and SEARCH. It is runtime-neutral (`Uint8Array`, no Node APIs), reaches storage only through `src/lib/imap/service.ts` and A2's `verifyMailAppPassword`, and could sit behind a future gateway. **`server/runtime/imap.ts`** and **`imap-limits.ts`** own the TLS socket, timers, per-instance limits, certificate reload and shutdown; `server/index.ts` starts it when `IMAP_PORT` is set. The distribution guard fails if anything the Worker compiles imports either, or if a Workers build contains the listener.
- **Capabilities** are exactly `IMAP4rev1 SASL-IR AUTH=PLAIN ID` before login and `IMAP4rev1 ID NAMESPACE UNSELECT SPECIAL-USE MOVE UIDPLUS IDLE` after (`session.ts`). Nothing else is advertised (no IMAP4rev2, CONDSTORE/QRESYNC, NOTIFY, LITERAL+, UTF8=ACCEPT); adding one needs its behavior implemented and tested first. UIDPLUS (A5.3) and IDLE (A5.4) extend only commands of the authenticated states, so like MOVE they are not listed before login.
- **Flags (A5.1, A5.2a, A5.2c):** SELECT answers `[READ-WRITE]` with `PERMANENTFLAGS (\Seen \Flagged)` for any principal that may read the mailbox, plus `\Deleted` for a principal with management access in every folder while bp0003 is installed (in Drafts also bp0004), because the web app lets every reader, `read_only` delegates included, mark read and star; EXAMINE answers `[READ-ONLY]` with `PERMANENTFLAGS ()`. STORE and UID STORE (FLAGS, +FLAGS, -FLAGS, each with .SILENT) change \Seen and \Flagged through A3's `storeImapFlags`, in chunks of at most 80 UIDs, each chunk re-authorized. \Answered, \Draft and keywords are accepted and not kept (the FETCH response shows the real flags); \Recent and unknown system flags are BAD. STORE changes \Deleted where it is a permanent flag (A5.2a; in Trash and Drafts since A5.2c, in Drafts only on the principal's own drafts, `NO [NOPERM]` otherwise); a FLAGS replace changes only the flags permanent for the principal, so a reader's never touches \Deleted. Naming \Deleted where it is not permanent refuses the whole STORE and writes nothing, not even the \Seen it also named: `NO [NOPERM]` without management access, `NO [CANNOT]` without bp0003, or in Drafts without bp0004. A permission denial never ends the session; lost access still ends it with BYE. Under SELECT, a non-PEEK `BODY[…]`, `RFC822` or `RFC822.TEXT` sets \Seen through the same write once the body has been read, and the response carries the new FLAGS; `BODY.PEEK`, `RFC822.HEADER` and EXAMINE never do. .SILENT still reports a flag that did not end up as requested (a concurrent change, or \Seen on outbound mail). The listener never calls the one-UID `setImapMessageFlags`.
- **EXPUNGE and CLOSE (A5.2a, A5.2c)** are recoverable everywhere but Trash and Drafts: A3's `expungeImapFolder` moves the messages marked \Deleted to Trash (see "Recoverable expunge (A5.2a)"). In Trash, and in Drafts for the principal's own drafts, they delete permanently (see "Permanent IMAP expunge (A5.2c)"); object-storage cleanup failures never change the answer. EXPUNGE first refreshes the view without EXPUNGE responses, so only UIDs the session has announced are candidates, then reports every message that left the folder, by this command or otherwise, highest sequence number first. It is `NO` under EXAMINE, `NO [NOPERM]` without management access and `NO [CANNOT]` without bp0003 (in Drafts without bp0004), and changes nothing then; a chunk refused after earlier chunks committed still reports what they removed. CLOSE does the same without untagged responses; under EXAMINE, without bp0003 (in Drafts bp0004) or for a principal without management access it only closes. If the move or deletion fails, CLOSE answers `NO [UNAVAILABLE]` and keeps the mailbox selected with its marks. UNSELECT never expunges. Lost access ends the session with BYE, as everywhere.
- **MOVE and UID MOVE (A5.2b, RFC 6851)** take a sequence set (or UID set) and a mailbox name in the same syntax as SELECT. Under SELECT only (`NO` under EXAMINE), the view is refreshed without EXPUNGE, the set is resolved against the sequence numbers or UIDs the client knows (UIDs that do not exist are ignored, as in UID FETCH), A3's `moveImapMessages` moves them (see "IMAP MOVE (A5.2b)"), and the view is refreshed with EXPUNGE: every message that left, by this MOVE or otherwise, is reported in the client's original sequence space, highest number first, before the tagged answer. Before those EXPUNGEs, a committed move sends `* OK [COPYUID <uidvalidity> <source-uids> <destination-uids>] Moved` (A5.3, RFC 4315 and RFC 6851 §4.3; see "UIDPLUS (A5.3, RFC 4315)" below). Refusals move nothing: `NO [NOPERM]` without management access or for another user's draft, `NO [CANNOT]` for a destination the policy refuses (including the same folder) or without bp0003, `NO [NONEXISTENT]` for an unknown destination (the session goes on). A message that had already left when the MOVE ran makes the answer `NO` after what did move is reported; a message a concurrent change kept in place (a deleted custom destination, a changed draft author) makes it `NO … could not be moved`. The spam training runs after the move and before the tagged answer; its failure is logged, never answered.
- **UIDPLUS (A5.3, RFC 4315).** `UID EXPUNGE <uid-set>` is EXPUNGE narrowed to the named UIDs, under SELECT only (`NO` under EXAMINE, BAD outside the selected state). The set is resolved against the UIDs the session has announced, after a refresh without EXPUNGE, so it costs one pass over the mailbox whatever range is sent, and a UID never announced (one above the highest, or one arriving while the command runs) is never a candidate. `expungeImapFolder` then intersects it with the folder's \Deleted UIDs up to that highest UID and runs exactly the A5.2a relocation (outside Trash and Drafts) or the A5.2c deletion (Trash, and Drafts for the principal's own drafts, after releasing stale Drafts UIDs), whose batches re-check the \Deleted mark on each exact UID, membership, bp0003/bp0004, authorship and authority in their own SQL; post-commit object cleanup is unchanged. A marked message outside the set, and a message in the set that is not marked, are untouched. The answer reports, as EXPUNGE does, every message that left the folder, highest sequence number first. MOVE's COPYUID comes from `relocateImapMessages`, which reads back, inside the same batch, the UID each moved message holds in the destination (the one just allocated, or one kept from an earlier stay) and that folder's UIDVALIDITY; source UIDs are ascending and the destination UIDs follow them position by position, written as ranges only for ascending runs. It is sent only for messages that moved, and not at all when nothing moved, a mapping is unknown, or a later chunk failed after earlier chunks committed (those still report their EXPUNGEs; COPYUID is a SHOULD for MOVE, and a partial one is never sent). COPYUID for COPY is owed only by a successful COPY, which does not exist yet; APPEND's APPENDUID is described under "APPEND (A5.7)". No schema change.
- **Mailbox management (A5.5a): CREATE, RENAME, DELETE** change custom folders only, through the R-1 folder-management service (`src/lib/mailboxes/folder-management.ts`), which decides authority (owner, or `full_access` delegate while sharing is enabled; the mail app password must still exist with the `imap` scope) and repeats it inside each write; the listener only resolves names and maps outcomes (`forbidden` → `NO [NOPERM]`; `notFound` → `BYE` when the session's own access is gone, otherwise `NO [NONEXISTENT]`). The namespace stays flat (`NIL` delimiter, `\Noinferiors`; `/` and `.` are ordinary characters).
  - **Strict IMAP naming** (`imapFolderNameVerdict` in `src/lib/imap/utils.ts`), for names created or renamed over IMAP only (web and JMAP keep their rules): names are decoded from modified UTF-7 (non-canonical encodings and raw 8-bit bytes are `NO [CANNOT]`); an existing folder's exact name, a system folder's canonical name (`Drafts`, `Sent`, `Archive`, `Spam`, `Trash`) or INBOX in any case is `NO [ALREADYEXISTS]`; a name equal to one of those up to case or Unicode NFC normalization, a `<base> (<n>)` shape whose base collides, `*` or `%`, surrounding whitespace, and anything R-1 refuses (empty, over 80 characters, control characters) is `NO [CANNOT]`. The service's `strictNames` mode repeats the ASCII case check inside the insert or rename (`lower(name)`), so two sessions cannot both take `Foo` and `foo`; SQLite folds ASCII only, so a racing non-ASCII case variant can still get through without a schema constraint, and the listing then disambiguates it like any other collision (no migration).
  - **Collision groups fail closed.** The listing lists colliding product names (case, NFC, or a system folder's name, e.g. a custom `Trash`) as `name (2)`, `name (3)`, … by age, and deleting one member can silently hand a suffix to another folder. RENAME and DELETE resolve the name to a folder id, then refuse (`NO [CANNOT]`) any folder whose name collides or that is named like a colliding base's suffix (`ambiguousFolderIds`), so a stale or reassigned name never changes the wrong folder. Such folders stay listed and selectable; they are renamed in the web app. System folders and INBOX are never renamed or deleted (`NO [CANNOT]`; INBOX's special RENAME semantics are not offered).
  - **RENAME** keeps the folder's id, so its IMAP identity (`f:<id>`), UIDVALIDITY and UIDs, and any selection of it, in this session or another, continue unchanged. Renaming to the same name is `NO [ALREADYEXISTS]`; a case-only rename of itself is allowed.
  - **DELETE** moves every message of the folder, snoozed ones included, to Trash and deletes the folder in one guarded, mailbox-scoped batch (R-1 `removeMessages`); nothing is deleted permanently. The folder this session has selected is `NO [INUSE]`; another session that has it selected ends with `BYE` at its next command or IDLE poll. The folder's `imap_folders` row is kept, so a folder later created under the same name gets a new id and a higher UIDVALIDITY.
  - **SUBSCRIBE / UNSUBSCRIBE (compatibility).** There is no stored subscription state: every visible mailbox is subscribed and LSUB lists them all, as before. SUBSCRIBE of a visible mailbox (any read access is enough) is `OK`; UNSUBSCRIBE is `NO [CANNOT] All mailboxes are always subscribed`; an unknown name is `NO [NONEXISTENT]`; neither writes anything. Deviation from RFC 3501: a subscribed mailbox that is deleted disappears from LSUB instead of staying subscribed. Stored subscriptions (A5.5b, a migration) are deferred until GUI-client testing shows they are needed.
  - Not certified with GUI clients.
- **APPEND (A5.7, RFC 3501 §6.3.11, with UIDPLUS APPENDUID).** `APPEND mailbox [flag-list] [date-time] literal`, into **Drafts only**, by its stable `drafts` key (a custom folder listed as `Drafts (2)`, INBOX and every other folder are `NO [CANNOT] APPEND is only available for Drafts`; an unknown name `NO [NONEXISTENT]`). No capability is added (APPEND is IMAP4rev1; UIDPLUS was already advertised); there is no LITERAL+, MULTIAPPEND, APPENDLIMIT, CATENATE or BINARY.
  - **Who:** the mailbox owner or a `full_access` delegate (management access): the principals who can also `\Deleted` and expunge their earlier draft versions, which is how clients replace a draft. `send_as`, `send_on_behalf` and `read_only` get `NO [NOPERM]` (stricter than web and JMAP draft creation, which accept send permissions; never weaker). Lost access (revoked credential, `imap` scope, disabled user or mailbox, sharing turned off) ends the session with BYE, as everywhere.
  - **Its own literal path.** The ordinary 64 KiB literal limit is unchanged. Once authenticated, the framer recognizes APPEND's message literal, hands the session the command up to it and holds (no continuation, nothing framed, reading paused). Everything that can be refused is refused before the continuation, so no octet of the message is read: syntax (flags as STORE takes them, \Recent and unknown system flags BAD; a malformed date-time BAD), `\Deleted` (`NO [CANNOT]`), the size (over 10 MiB `NO [LIMIT] Message too large`; empty `NO [CANNOT]`), the mailbox, the permission, then an upload permit. Only then is one buffer of exactly the announced size allocated and `+` sent; the octets go there and nowhere else (no command queue, no byte string), then the rest of the line must be empty, and framing resumes at the exact next octet, so command-looking lines in a message are data and a pipelined command runs normally.
  - **Limits.** 10 MiB (10,485,760 octets), defined as JMAP's `maxSizeUpload` itself (`MAX_APPEND_SIZE`), the existing limit for a client turning raw MIME into a draft. Upload permits are a second `ContentReadLimiter`: 4 in all (`maxConcurrentAppends`), 1 per user (`maxConcurrentAppendsPerUser`), separate from the content-read permits, taken before the continuation (waiting allocates nothing) and held through receipt, parsing, storage, commit and the answer. The literal must arrive within an absolute deadline from the continuation, `appendLiteralBaseMs` (60 s) plus its size at `appendLiteralMinBytesPerSecond` (16 KiB/s), about 11.7 minutes for 10 MiB; its octets never extend it; on expiry `* BYE Autologout` and the connection closes. Disconnect, timeout and shutdown mid-literal store nothing and release the permit.
  - **Memory.** Receiving holds the message once (one N-octet buffer). Parsing it with postal-mime (the same parser JMAP import and SMTP intake use) costs several times more for text-heavy mail: four simultaneous 10 MiB text-heavy APPENDs (the global limit) measured about 6x the messages in sampled heap and about 640 MiB of RSS growth in the test process, with event-loop stalls under about 200 ms. Moving parsing off the event loop is deferred.
  - **Bytes and metadata.** The literal is stored byte for byte under `drafts/<messageId>.eml` (no CRLF normalization, header changes or re-encoding), so FETCH serves it exactly and RFC822.SIZE is its length. The columns the web app and JMAP read are parsed from it as JMAP Email/import does (`parseRawMime`), with the same rules: a From the principal may send from in this mailbox (`getAuthorizedSenderAddress`; otherwise `NO [CANNOT]`, as for a message without From), the existing attachment limits (`NO [LIMIT]`), attachments stored under server-generated ids (`attachments/<messageId>/<attachmentId>/<name>`). `\Flagged` stars the draft; `\Seen` and `\Draft` are implied (drafts are outbound and in Drafts); `\Answered` and keywords are accepted and not kept. The date-time sets INTERNALDATE (`created_at`); without one it is now, never the Date header, which is not touched. The draft is the principal's own (`user_id`), read, threaded by `resolveThreadId`.
  - **Order and atomicity** (A3's `appendImapDraft`). Objects first (raw, then attachments), then one guarded batch (`insertImapDraft`): the Drafts state row if missing, the `messages` row only while `authorityGuard` holds, the attachment rows, then the UID from UIDNEXT bound to the raw key, the exact size and the draft fingerprint (attachment rows first: bp0004's attachment trigger releases a draft's Drafts UID), and the UID and UIDVALIDITY read back. The tagged answer is `OK [APPENDUID <uidvalidity> <uid>] APPEND completed` from that read-back, the UID a later SELECT and UID FETCH show; a later sync keeps it. Unlike JMAP Email/import (row first, object after), no draft is ever visible without its bytes. A failed write or batch, or authority lost by the commit, commits nothing (UIDNEXT included) and removes every object written, best effort (`NO [UNAVAILABLE]`, or BYE/NOPERM for lost access); an object a crash leaves behind is unreferenced and never served. The `imap` scope is checked by `authorizeImapAccess` before the literal and when processing starts, not inside the batch (as for A5.2c).
  - **After the commit.** A session with any mailbox selected is refreshed before the tagged answer (Drafts: `EXISTS`); other sessions, IDLE included, learn of it through the mailbox revision as for any change. A client that loses the tagged answer and retries creates a second draft: the usual IMAP ambiguity; there is no Message-ID deduplication.
  - **Deferred:** APPEND to other folders (Sent copies belong with a future SMTP submission service), `send_as`/`send_on_behalf` APPEND, COPY, LITERAL+, MULTIAPPEND, APPENDLIMIT, CATENATE, BINARY, quotas, an orphan-object reconciler, off-loop MIME parsing. Not certified with GUI clients.
- **Not writable yet:** COPY is refused before any storage call; permanent deletion exists only as EXPUNGE, UID EXPUNGE and CLOSE in Trash and Drafts (A5.2c, A5.3). A3's own UID and canonical-size bookkeeping still happens on reads, as A3 intends.
- **Names:** a flat namespace with a `NIL` hierarchy delimiter, so every folder name (which may contain `/` or `.`) is exposed exactly as A3 names it, in modified UTF-7. Only INBOX is case-insensitive.
- **Sequence numbers** exist only in the session: a snapshot of A3's UIDs taken at SELECT and diffed against A3 before each command, with EXPUNGE withheld during FETCH and SEARCH (RFC 3501 §7.4.1). A UIDVALIDITY change or a vanished selected folder ends the session with BYE.
- **Content:** FETCH serves A3's canonical octets exactly. BODYSTRUCTURE, BODY, sections and ENVELOPE are derived from those same octets by an offset-based reading (`mime.ts`), never from database columns or rebuilt MIME. SEARCH answers header and body keys from those octets too. Derived metadata is cached per (mailbox, folder key, UIDVALIDITY, UID), which A3 guarantees is immutable.
- **Authentication** is A2 with the `imap` scope, then `authorizeImapAccess`; A3 re-authorizes each command and the listener re-checks idle sessions every 60 seconds, closing revoked ones with BYE.
- **IDLE (A5.4, RFC 2177)** is accepted in the authenticated and selected states (EXAMINE included) and changes neither. After `+ idling` the framer takes the next line raw (the continuation-line mode AUTHENTICATE also uses): `DONE`, exactly and case-insensitively, ends it with `OK IDLE completed` and input after it is framed as usual; any other line ends it with `BAD Expected DONE` and is then run as a command, except one announcing a literal, which ends the session with BYE. Input sent before the `+` is accepted only as a leading DONE.
  - **The database is authoritative; there is no process-local event path.** The realtime hub is not used, so an IDLE session learns of changes made by any instance sharing the database. Each poll (every 10 s ±20%, starting at once) calls A3's `getImapChangeSignal`: it re-authorizes the principal (a revoked app password or `imap` scope, removed access, a disabled user or mailbox, sharing turned off: BYE; a downgrade to `read_only` keeps idling and later writes answer NOPERM as before), then reads the mailbox's `jmap_mailbox_revisions` row and the selected folder's UIDVALIDITY, each one indexed lookup. A changed UIDVALIDITY ends the session with BYE; a moved revision runs the existing refresh (EXPUNGE highest first, FETCH FLAGS, EXISTS, A3's usual UID bookkeeping, never \Seen or other writes). The signal is read before refreshing and kept only after the refresh succeeded, so a change during it is seen at the next poll; it and the reconciliation schedule survive repeated IDLE/DONE, so those never force a refresh.
  - **Reconciliation.** The revision moves with every insert, update and delete of the mailbox's `messages` and `folders`, but not with IMAP-only state: a \Deleted mark set or cleared by another session, a Drafts UID released by an attachment-only change, a restored UIDVALIDITY (read by the poll itself). So the selected view is also refreshed unconditionally every 300 s ±20%, which bounds how late those appear; no IMAP revision counter was added (no schema change).
  - **Liveness and limits.** `* OK Still here` after 120 s without any write, never while a write is pending; writes are awaited, so a client that stops reading stalls the loop instead of queueing output. Autologout counts the client's complete commands and continuation lines only (IDLE and its DONE included; see "Resource limits (A5.6)"), never the server's own writes. A poll failure is logged and retried; authority unconfirmable for 60 s (the database failing while authorizing) ends the session with BYE, and 120 s without a successful poll with `BYE [UNAVAILABLE]`; the server never ends IDLE with a tagged answer. All waits are host delays that DONE, disconnect or shutdown cancel. Timings are `ImapLimits` fields (`idlePollMs`, `idlePollJitter`, `idleReconcileMs`, `idleKeepaliveMs`, `idleAuthUncertainMs`, `idleUnavailableMs`); no environment variables yet.
  - **Not certified with GUI clients.** The protocol tests (a virtual clock in the in-memory harness, and the real TLS listener) are not Thunderbird, Outlook, Apple Mail/iOS or Android certification, which remains a later empirical step.
- **Resource limits (A5.6).** Per connection and per instance; no schema change and no environment variables (`ImapLimits` gained `loginTimeoutMs` and `maxConcurrentReadsPerUser` only).
  - **Login deadline.** A connection not authenticated 60 s (`loginTimeoutMs`) after its greeting gets `* BYE Autologout` and is closed. The deadline is absolute: bytes, NOOPs, partial lines, literals and failed attempts never extend it.
  - **Autologout** (60 s before authentication, 30 minutes after, as before) counts only complete framed items: a command, a continuation line (IDLE's DONE, an AUTHENTICATE response) or a framing error. Raw octets, a partial line or literal, and the server's own writes (keepalives, notifications, `+` continuations) are not activity. Both timers run in the session on the host's clock (`ImapSessionOptions.timeouts`), so they are tested on the virtual clock; the listener passes its limits and no longer keeps an input timer.
  - **Line length.** 8 KiB before authentication (`PREAUTH_MAX_LINE`), 64 KiB after, enforced by the framer as octets arrive (a line over the limit ends the session with BYE before its newline). Literal limits (1 KiB before authentication, 64 KiB after, 16 per command), the 16-command queue and the absence of LITERAL+ are unchanged (APPEND, added in A5.7, has its own literal path; see "APPEND (A5.7)").
  - **Content permits.** Work on message content (FETCH items that need the octets, SEARCH keys answered from them) takes a permit from `ContentReadLimiter` (`imap-limits.ts`): 8 in all (`maxConcurrentReads`) and 2 per user (`maxConcurrentReadsPerUser`), the user's permit first, so a user at its limit waits without holding a global one. FETCH holds the permit from reading a message until its response has been written, so a client that stops reading holds at most its own user's two permits and other users proceed; SEARCH holds one per message while reading it. Metadata-only FETCH and SEARCH take none. Permits are released on errors, disconnect and shutdown.
  - **FETCH memory.** A whole-message FETCH (`BODY[]`, `RFC822`) serves the stored octets without making the byte string MIME parsing uses (`MessageView.text` is lazy), and responses are written in parts (`ResponseBuilder.parts()`): a literal of 64 KiB or more is written as it is, never copied into one response buffer. A stalled 16 MiB FETCH retains about one copy of the message (it was about three).
  - **SEARCH.** Sequence-number and UID keys are compiled into range matchers the size of the key as written (`sequenceMatcher`), never a mailbox-sized set per key.


## Downstream changes to offer upstream

- `40720fb` — manual domain setup without Cloudflare credentials, manual-mode MX setup, inbound SMTP recipient validation.
- A5.2b — `src/lib/spam/feedback.ts`: the training part of `applySpamFeedback` as `spamTrainingStatements`, reusable without moving the message, and guarded on the `spam_feedback` row so two concurrent or repeated trainings of one message no longer count twice.
- R-1 (security) — JMAP `Mailbox/set` (`src/lib/jmap/mailboxes.ts`) now manages folders through `src/lib/mailboxes/folder-management.ts`. Upstream had three flaws there: `update` (rename) checked no permission, so `read_only`, `send_as` and `send_on_behalf` delegates could rename a shared mailbox's folders; `destroy` with `onDestroyRemoveEmails` ran `UPDATE messages … WHERE folder_id = ?` without any mailbox scope before checking that the folder belonged to the mailbox named in the id, so any user with a mailbox of their own could move another mailbox's messages to Trash given a folder id (a current or former delegate knows them), while the answer claimed the folder was destroyed; and its emptiness check ignored snoozed messages, whose folder the foreign key then cleared, silently moving them to Inbox. The service authorizes with `getMailboxAccessLevel`'s `canManage` (owner, or `full_access` delegate while sharing is enabled), then repeats that authority inside every write (enabled user and mailbox, ownership or delegation, and for a mail app password its existence with the `imap` scope, via `json_each`), each run as one D1 batch; every statement is scoped to the authoritative mailbox and a folder verified to belong to it; deletion requires emptiness (snoozed mail included) in the deleting statement, and `onDestroyRemoveEmails` moves only that mailbox's messages of that folder in the same batch. Rename validates like create (string, trimmed, 1–80 characters, no C0/DEL controls) and exact duplicates are `invalidProperties` instead of `serverFail`; nothing is reported `updated` or `destroyed` unless it happened, and a folder of another mailbox is `notFound` without revealing whether it holds mail. No schema change. Case-only duplicates, names equal to system folders and NFC/NFD variants are still accepted (A5.5 decides). The web `POST /api/folders` route was already correctly authorized and is unchanged. Tests: `tests/folder-management.test.mjs`; D1: `scripts/imap-state-d1-check.mjs`.
- A5.2a — `server/runtime/sqlite-database.ts`: `batch()` awaited between BEGIN and COMMIT, so another caller's query on the shared connection could run inside the transaction (and be rolled back with it after reporting success) and a concurrent batch failed with a nested BEGIN. It now runs the whole transaction synchronously (`tests/sqlite-batch.test.mjs`).
